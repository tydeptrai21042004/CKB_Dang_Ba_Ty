# CKBuilder v10 AgentOS — v10.0.1

CKBuilder v10 upgrades the v9 service hub into a safer CKB agent operations layer. The model remains unable to hold private keys, sign transactions, broadcast transactions, mutate Fiber channels, or execute real payments autonomously. v10 focuses on completing the workflow around those boundaries: build and validate intents, obtain human approval, verify external execution, and preserve cryptographically attributable evidence.

## v10.0.1 provider/runtime reliability patch

### Gemini 3 direct GenerateContent compatibility

The Gemini BYOK adapter now uses current direct GenerateContent field names and preserves provider-specific function-calling state across stateless turns. In particular, CKBuilder replays the complete Gemini model `content.parts` returned by the provider, including opaque `thoughtSignature` values, and then sends ID/name-matched `functionResponse` Parts for tool results. Parallel function calls receive a corresponding response Part even when CKBuilder's local executable-tool budget is exceeded, so provider response cardinality stays valid.

New Gemini selections default to `gemini-3.7-flash`. Explicit user model IDs remain allowed. CKBuilder no longer applies its low generic `temperature` value to Gemini 3.x requests. Upstream Gemini/provider errors are surfaced as sanitized HTTP 502 gateway failures instead of being confused with local 400 request-validation failures.

The browser continues to keep BYOK keys only in the current tab/session memory; the key is not written to CKBuilder server storage.

### Runtime CI versus release CI

A running local project legitimately contains `.env`, `secrets/`, `node_modules/`, and project-owned runtime state. These paths must be rejected from a distributable release archive, but their existence is not a runtime test failure. v10.0.1 therefore separates:

```bash
npm run ci:runtime   # safe for a live local workspace
npm run ci:local     # runtime checks + clean-release audit
```

`check-env-and-run-all.sh` calls `ci:runtime`. Run `ci:local` only from a clean release copy/archive.

## What changed

### 1. Persistent service identity and signed receipts

Each deployment creates one Ed25519 service identity under `DATA_DIR/private/agent-service-identity.json` with file mode `0600`. Completed service receipts use `ckbuilder-agent-job-receipt/v2`: the existing SHA-256 content/anchor binding is retained for compatibility and an Ed25519 signature proves which CKBuilder service identity issued the receipt. The public receipt contains only the public key/fingerprint and signature.

### 2. SQLite agent-job persistence

`agent-jobs.json` is replaced by `agent-jobs.sqlite` using WAL, indexed job/service timestamps, timing-safe access-token comparison, and one-time migration of a legacy JSON ledger. Reputation now records signed-receipt count/rate in addition to fulfillment and evidence success.

### 3. Exact-operation community MCP approval

An approval now includes both the tool name and a canonical SHA-256 hash of its arguments. When an exact approval is present, a legacy tool-name approval cannot override an argument mismatch. Signing, broadcasting, payment, channel-mutation, and secret-handling MCP tools remain hard-blocked.

### 4. Hardened MCP 2026 transport

The MCP client keeps 2026-07-28 request metadata, supports `server/discover`, bounded responses, authorization headers, no-follow redirects, direct private-IP blocking, and DNS resolution checks for real remote requests. Localhost HTTP remains supported for local development.

### 5. Observable multi-agent workflow DAG

Team services now expose `ckbuilder-agent-workflow/v1`. Specialist nodes have no mutual dependency and execute concurrently; the synthesis node explicitly depends on every specialist. Node state, step counts, and timestamps are retained in the job record and the workflow hash is bound into the signed receipt. Single-agent services also expose a one-node workflow rather than an implicit hidden loop.

### 6. CKB transaction intent builder

`POST /api/agent-commerce/transaction-build` and `npm run agent:tx:build -- input.json` build an **unsigned** capacity-transfer intent from supplied live Cells or read-only Indexer discovery. The builder performs Cell selection, target/change construction, fee accounting, and static preflight. It deliberately does not guess protocol-specific occupied-capacity policy, witnesses, CellDeps, signatures, or broadcast behavior.

### 7. Fiber settlement verification

The existing quote path still forces `send_payment(dry_run=true)`. v10 adds `POST /api/agent-commerce/fiber-payment-status`, which accepts a payment hash and uses only `get_payment` to verify status after a human/external wallet executes the real payment.

### 8. Official CKB Dev Skills evidence tool

The official-docs plugin adds `ckb_dev_skills`, providing a live official CKB AI-resource surface alongside the existing LLM documentation corpus.

## Safety boundary

```text
Agent -> read/plan/build -> deterministic validation -> approval intent
                                                   |
                                                   v
                                             Human wallet
                                                   |
                                      sign / broadcast / pay
                                                   |
                                                   v
Agent <- signed receipt <- result verification <- chain/Fiber
```

The AI runtime never receives a private key and never gains transaction signing, transaction broadcast, real Fiber payment, or channel-mutation authority.

```bash

```
