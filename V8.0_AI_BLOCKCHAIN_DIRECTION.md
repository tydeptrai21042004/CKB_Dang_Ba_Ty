# CKBuilder v8 — AI × Blockchain Direction and Implementation

CKBuilder v8 was designed after comparing current AI/blockchain agent systems with the practical needs of the CKB/Fiber community. The goal is not to clone another chain's token model. The useful patterns are translated into CKB-native products with conservative signing and settlement boundaries.

## What current projects teach us

| Project/direction | Useful pattern | What CKBuilder adopts | What CKBuilder deliberately does not copy |
|---|---|---|---|
| Coinbase AgentKit / Agentic Wallets | Agents need scoped on-chain capabilities, wallet guardrails, and machine payments | Explicit action/settlement boundary and Fiber payment intents/quotes | Unrestricted autonomous wallet control |
| elizaOS | Plugins make an agent useful across many services and communities | Built-in + community MCP plugin catalog, permissions, discovery, audit | Loading arbitrary community JavaScript inside CKBuilder |
| Olas Mech Marketplace | Agents can discover/hire specialized agent services | Agent Service Hub and community MCP service delegation | Automatic crypto spending without user approval |
| Virtuals ACP | Agent jobs benefit from explicit agreement, payment, result, evaluation/receipt stages | Service contracts, expected outcomes, payment intent, cryptographic job receipt | Tokenizing every agent or requiring a proprietary agent token |
| Fetch.ai / ASI Agentverse | Agent identity, discovery, specialization, and multi-agent orchestration matter | Multi-specialist launch-readiness team and service discovery | A new global discovery chain/protocol inside CKBuilder |
| NEAR AI Cloud | Privacy/verifiability of inference can matter for agent workloads | Optional NEAR AI Cloud BYOK provider alongside existing providers | Making CKB depend on NEAR or moving CKB state to another chain |
| Gaia / decentralized AI | Domain-owned knowledge/services can be exposed as agent infrastructure | Community MCP services + current CKB docs/repository evidence | Claiming decentralization merely because an LLM endpoint is remote |
| CKB AI / CKB Dev Skills | CKB-specific AI should use current docs, RPC/dev tools, and maintained workflows | CKB AI MCP compatibility, official docs, CKB/Fiber tools, mission/service workflows | Treating alpha community AI output as authoritative over official docs or chain evidence |

## v8 product direction

### 1. CKB Agent Service Hub

A user chooses a **service** with a defined audience, expected outcome, evidence sources, settlement mode, and trust boundary. Community MCP plugins are automatically surfaced as delegatable community services when enabled.

This is closer to an agent marketplace/service network than a blank chatbot, while avoiding a speculative token layer.

### 2. Multi-agent CKB Launch Readiness Team

`ckb-launch-readiness-team` coordinates three specialists:

1. **Ecosystem Researcher** — current CKB tooling/releases/issues/docs.
2. **Security & Build Reviewer** — architecture and optional local workspace review.
3. **Network Operator** — optional live CKB/Fiber readiness evidence.

A final release-chair agent reconciles the reports into one `GO`, `CONDITIONAL GO`, or `NO-GO` decision. Missing RPC/workspace configuration remains explicitly unverified.

### 3. Fiber agent-commerce simulation

Fiber is a natural CKB rail for high-frequency machine-to-machine payments. v8 adds a payment quote path that calls FNN `send_payment` **only with `dry_run=true` forced by the server**.

The output is a `ckbuilder-fiber-payment-intent/v1` object with:

- dry-run route/fee evidence;
- network and request details;
- `autonomousSpend: false`;
- `requiresHumanExecution: true`;
- a clear execution boundary.

No real payment, signing, channel mutation, or broadcast is exposed to the model.

### 4. Verifiable agent-job receipts

Every completed agent service can return `ckbuilder-agent-job-receipt/v1` containing hashes of:

- the user objective;
- final output;
- tool/evidence trace;
- optional Fiber quote;
- model/provider/agent execution metadata.

The receipt includes an application-defined digest payload that can later be stored by a human-controlled wallet in a CKB Cell or referenced from a Spore object. This is **not claimed as an official CKB standard**.

This creates a useful primitive for research reports, audits, grant work, service delivery, and agent-to-agent tasks: the result can be independently fingerprinted even if settlement happens elsewhere.

### 5. Private/verifiable inference option

v8 adds **NEAR AI Cloud** as another explicit BYOK provider through its OpenAI-compatible endpoint. It is optional; CKBuilder remains provider-neutral and CKB-specific state/evidence stays within the existing tool boundary.

## Security invariants retained

- AI never receives or requests private keys, seeds, mnemonics, or issuer secrets.
- CKB `send_transaction` remains unavailable.
- Fiber real `send_payment`, channel open/close, and other value-moving operations remain unavailable to model tool calls.
- Community MCP tools that look like signing, broadcast, payment, or channel mutation remain hard-blocked.
- Unannotated non-read-only MCP tools still require explicit one-run approval.
- Job receipts are evidence fingerprints, not proof that model reasoning is correct.
- Official docs and deterministic chain/RPC evidence outrank LLM assertions.
