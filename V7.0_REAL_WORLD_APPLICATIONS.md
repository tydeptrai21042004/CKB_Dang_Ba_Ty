# CKBuilder v7.0 — Real-World CKB Mission Control

## Why v7 exists

v6 proved that CKBuilder could run bounded multi-step AI agents and safe MCP/community tools, but a generic tool workbench still required users to know what to ask and which tools to enable. v7 makes the product job-oriented: each mission defines an audience, evidence sources, required runtime configuration, specialist agent, deliverables, and safety contract.

The design follows current CKB ecosystem guidance rather than inventing generic Web3 workflows:

- CKB's official AI-agent resources recommend current official docs, CCC for dApps, `ckb-testtool` / `ckb-debugger` for Script work, OffCKB for local development, and Fiber for payment-channel work: <https://docs.nervos.org/docs/ai-agents/ai-resource>
- Fiber is a peer-to-peer payment and swap network with channels, routing, multi-hop payments, multiple assets, and actively evolving APIs: <https://github.com/nervosnetwork/fiber> and <https://docs.fiber.world/developer/rpc>
- CKB's Rust Script quick start points developers to `ckb-testtool` for regular testing and `ckb-debugger` for deeper analysis: <https://docs.nervos.org/docs/script/rust/rust-script-quick-start>
- CCC is the maintained JS/TS application/wallet integration path in current CKB documentation: <https://docs.ckbccc.com/>
- Spore/DOB and RGB++ provide concrete asset/digital-object/Bitcoin-linked application domains rather than abstract token examples: <https://github.com/sporeprotocol/spore-sdk> and <https://docs.rgbpp.io/>

## Product model

A mission is a deterministic workflow wrapper around the tool-using agent runtime:

```text
user goal
  -> mission contract
  -> specialist agent
  -> fixed evidence plugin set
  -> bounded tool loop
  -> auditable tool trace
  -> deliverable-oriented answer
```

`src/lib/application-service.js` is the application registry. `POST /api/ai/application` executes a mission. The generic `/api/ai/agent` route is still available for expert/custom use.

## Real-world missions

### 1. Fiber Node Operator Diagnostics

**Problem:** a node is online but routes/payments fail, peers are unstable, or the operator needs a quick health picture.

**Evidence:** configured Fiber JSON-RPC `node_info`, peers, channels, payments, graph nodes/channels.

**Output:** health summary, observed evidence, likely causes, safe next checks, unknowns.

**Boundary:** no `send_payment`, `open_channel`, `shutdown_channel`, signing, secret handling, or wallet mutation.

### 2. CKB Transaction Failure Lab

**Problem:** a transaction is rejected or a Script-integrated transaction behaves unexpectedly.

**Evidence:** transaction status, live Cells, Indexer Cell lookup/capacity, raw-transaction dry run, official docs.

**Output:** transaction shape, Script/cycle evidence, ranked root causes, smallest reproducible check path.

**Boundary:** `dry_run_transaction` is allowed; `send_transaction` is not an agent tool.

### 3. CKB Script Debug & Test Lab

**Problem:** a Lock/Type Script passes some tests but fails in a realistic transaction or deployment.

**Evidence:** explicitly approved source workspace + official Script/testing docs + optional chain RPC.

**Output:** suspected boundary, source evidence, ckb-testtool/ckb-debugger reproduction path, test matrix, version/deployment checks.

**Boundary:** read/search files only; no shell; no `.env`, keys, seed/mnemonic, keystore, or directory escape.

### 4. xUDT / Spore / RGB++ Asset Investigator

**Problem:** wallets/explorers/marketplaces need to explain what a Cell/transaction represents and what provenance is actually verifiable.

**Evidence:** CKB Cells/type Scripts/transactions plus current protocol docs.

**Output:** Cell/type inventory, protocol-identification evidence, state/ownership transition explanation, provenance limits.

### 5. CKB Community Contribution Finder

**Problem:** a newcomer knows TypeScript/Rust/backend/etc. but cannot find a useful first CKB contribution.

**Evidence:** current open issues and project activity from allowlisted repositories, current Nervos Talk topics, official prerequisite docs.

**Output:** candidate issues, fit rationale, prerequisite reading, one small first milestone, maintainer questions.

### 6. Protocol & Ecosystem Research Brief

**Problem:** researchers/proposal teams need current evidence, not model-memory claims, for choices such as Fiber vs on-chain transfers, CKB-native assets, or integration strategy.

**Evidence:** current official docs + repository activity + community discussion.

**Output:** facts separated from inference, alternatives, risks/unknowns, and a prototype/research agenda.

### 7. CKB dApp Architecture Advisor

**Problem:** a team has a product idea but does not know where Cells, CCC, xUDT, Spore, RGB++, or Fiber actually belong.

**Evidence:** current official/community references.

**Output:** component map, recommended protocol/tool fit, transaction/state boundaries, MVP milestones, security/operability risks.

### 8. CKB Testnet Launch Gate

Release gate for network configuration, Script deployment metadata, RPC evidence, signing boundaries, observability, and rollback readiness.

### 9. CCC Wallet Integration Readiness

Maps connect/account/network state, transaction intent construction, explicit user signing, submit/confirm/retry behavior, and browser/wallet regression tests.

### 10. xUDT Token Launch Planner

Covers token identity, xUDT Cell data, issuance authority, transfer conservation, wallet/indexer discovery, and Testnet scenarios.

### 11. Spore / DOB Creator Launch

Covers digital-object state, create/transfer/read flows, provenance boundaries, rendering/indexing, and missing/tampered metadata cases.

### 12. RGB++ Integration Review

Separates Bitcoin, CKB, synchronization/indexing, and wallet-confirmation responsibilities and adds delay/reorg/mismatch recovery scenarios.

### 13. CKBuilder Credential Trust Audit

Traces evidence review, issuance, signatures, issuer binding, on-chain/off-chain checks, revocation, public proof, passport, privacy, and tamper states.

### 14. CKB RPC Incident Response

Scopes production impact, collects node/indexer evidence, distinguishes upstream and application faults, defines non-destructive containment, and verifies recovery.

### 15. Fiber Liquidity & Routing Planner

Uses read-only node/channel/graph/payment evidence to rank liquidity and routing causes while keeping every channel/funding/payment change behind human control.

Every mission exposes 4--5 ordered `workflow` stages through `/api/config`; stages are also embedded into the execution contract so the UI description and agent task remain aligned.

## Configuration and trust

```bash
# Existing CKB RPC/Indexer endpoint
CKB_RPC_URL=http://127.0.0.1:8114

# Optional Fiber mission evidence
FIBER_RPC_URL=http://127.0.0.1:8227

# Optional Script/project mission evidence
CKB_AGENT_WORKSPACE=../my-ckb-project

# Optional server-only GitHub API token
CKB_GITHUB_TOKEN=
```

The browser receives only readiness metadata such as `missingConfig: ["FIBER_RPC_URL"]`; endpoint values, workspace paths, and GitHub tokens are not exposed through `/api/config`.

## Community extension path

Community projects can still contribute data-only MCP manifests under `plugins/community/`. v7 intentionally keeps executable local plugin code inside the reviewed CKBuilder core. Remote MCP tools inherit the v6 trust model:

- explicitly read-only tools may execute;
- unannotated external tools require a visible one-run approval;
- signing/broadcast/private-key/seed/mnemonic operations are hard-blocked;
- Fiber payment and channel mutation names are also hard-blocked;
- all tool output is returned to the model as untrusted data;
- every call is recorded in `toolTrace`.
