# CKBuilder Passport v3.0 implementation summary

## Implemented for real use

### Public product
- Builder Passport lookup by recipient Lock Script hash.
- Public credential verification remains deterministic and read-only.
- Portable W3C VC 2.0-shaped credential JSON endpoint.
- Verification QR endpoint (`qrencode` in the production image).
- Evidence submission with private tracking token.
- Deterministic evidence checks: CKB transaction status via configured RPC and GitHub repository accessibility via the public GitHub API.
- Optional AI certificate-image field extraction (PNG/JPEG/WebP).
- Optional AI evidence triage.
- Optional AI explanation of deterministic verification.
- Optional curriculum tutor.

### Bring-your-own-key AI
- No AI key in `.env` is required.
- User enters the provider key in the UI.
- Key is kept only in browser memory for the tab; provider/model preference may be stored in session storage but the key is not.
- Supported provider presets: OpenAI, OpenRouter, Groq (OpenAI-compatible chat endpoint pattern).
- Key is forwarded only for the requested AI operation and is not persisted or included in audit/credential data.
- AI has no signing, approval, issuer-registry, or transaction authority.

### Issuer/reviewer portal
- Separate server process from the public verifier.
- PBKDF2-SHA256 password storage.
- HMAC-signed, HttpOnly, SameSite=Strict admin session cookie.
- Login throttling.
- Evidence queue, deterministic checks, optional AI triage, request-changes/reject/approve actions.
- Human approval creates the credential; AI never auto-approves.
- Credential revocation UI and audit events.
- Private issuer service is loopback-only by default in Docker Compose.

### Credential workflow
- Generalized `ckbuilder-credential/v2` while continuing to accept legacy `ckb-degree-credential/v1` records.
- Prepare → CKB commit → persistent ACTIVE credential issuance path.
- Prepare → CKB revocation commit → persistent REVOKED path.
- Explicit operation records and failure states.
- `CHAIN_WRITE_MODE=required` available for real Testnet/Mainnet deployment.

### Persistence
- SQLite WAL product database for submissions, profiles, admin users, operations, and audit history.
- Existing signed credential ledger retained for protocol compatibility.
- This is deployment-ready for a single host. Active-active multi-host deployment still calls for a PostgreSQL adapter.

### Network/deployment
- Environment validation accepts `mainnet`.
- CCC client selection supports `ClientPublicTestnet` and `ClientPublicMainnet`.
- system/deployment-script parsing is network-aware (`devnet`, `testnet`, `mainnet`).
- Dockerfile (Node 22 + `qrencode`).
- Two-service production Compose file.
- `.env.example`, `.gitignore`, executable launchers, production configuration audit.
- `PRODUCTION_DEPLOYMENT.md` describes Testnet → Mainnet promotion.

## Deliberately not changed in-place

The deployed v1 credential-revocation Type Script still guarantees an irreversible state transition for one credential Cell lineage but does not implement a global singleton issuer registry. The issuer service now refuses a duplicate live record before creation, and the public verifier remains fail-closed on duplicate live Cells. Replacing this with an issuer-registry/SMT contract is a **breaking protocol migration**, not a safe application-layer patch, because existing deployed Cell data and Type Script code hashes would change.

For a first real deployment, keep the v1 contract, run `CHAIN_WRITE_MODE=required`, use one controlled issuer, and treat any duplicate live record as a hard conflict (current behavior). Introduce a v2 registry contract only with an explicit migration/testnet rollout.
